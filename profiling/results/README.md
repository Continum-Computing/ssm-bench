## Naming Convention

Result directories follow the pattern: `{gpu}-{platform}-{date}`

- **gpu**: GPU model name in lowercase (e.g., `t4`, `a100`, `h100`)
- **platform**: Execution platform (e.g., `colab`, `modal`, `local`)
- **date**: ISO 8601 date format `YYYY-MM-DD`

Examples:
- `t4-colab-2026-10-10` — Tesla T4 on Google Colab, October 10, 2026
- `a100-modal-2026-10-10` — A100 on Modal, October 10, 2026
- `h100-local-2026-11-15` — H100 on local machine, November 15, 2026

## File Descriptions

### `manifest.json`

Top-level index of all result sets. Contains:
- List of all available result sets with metadata
- Quick summary of key findings
- Pointers to analysis documents

### `metadata.json` (per result set)

Detailed metadata for a single benchmark run:
- **run_id**: Unique identifier
- **timestamp**: When the benchmark was executed
- **platform**: GPU specs and execution platform
- **software**: Python, PyTorch, CUDA versions
- **configuration**: Benchmark parameters (sequence lengths, state dimensions, etc.)
- **summary**: Aggregated statistics (average latency, utilization)
- **key_findings**: One-line summary of results
- **files**: List of files in this result set

### `benchmark_results.json` (per result set)

Raw benchmark data containing all measurements:
- Per-configuration results (latency, bandwidth, compute, arithmetic intensity)
- Statistical measures (mean, std, min, max, median, P95, P99)
- Hardware utilization metrics

### `benchmark_summary.txt` (per result set)

Human-readable summary generated by the benchmark runner. Contains:
- GPU specifications
- Benchmark configuration
- Average performance metrics
- Key findings

### `plots/` (per result set)

Visualization plots generated from the benchmark data:
- **latency_vs_seq_len.png**: Latency scaling with sequence length
- **bandwidth_utilization.png**: Memory bandwidth utilization
- **compute_utilization.png**: Compute unit utilization
- **roofline_model.png**: Roofline analysis (arithmetic intensity vs performance)

### `analysis/`

Cross-result analysis documents:
- **gpu_comparison_t4_vs_a100.md**: Detailed comparison of T4 vs A100 results

## How to Reproduce Results

### Prerequisites

- Python 3.11+
- PyTorch 2.0+ with CUDA support
- NVIDIA GPU (or cloud GPU access via Modal/Colab)
- matplotlib, numpy

### Running Benchmarks

```bash
# Install dependencies
pip install torch matplotlib numpy

# Run benchmarks (requires GPU)
python profiling/run_benchmarks.py \
  --seq-lens 512 1024 2048 4096 \
  --state-dims 64 128 256 \
  --input-dim 256 \
  --output-dim 256 \
  --dtype bf16 \
  --device 0 \
  --output profiling/results/{gpu}-{platform}-{date}/benchmark_results.json
```

### Generating Visualizations

```bash
python profiling/visualize.py \
  profiling/results/{gpu}-{platform}-{date}/benchmark_results.json
```

Writes into the directory holding that JSON: four PNGs under `plots/` and one `benchmark_summary.txt` beside it. Pass `--run-dir` to write somewhere else. No GPU is needed, since everything is recomputed from stored data.

### Running on Modal (Cloud GPU)

```bash
# Install Modal
pip install modal
modal setup

# Run benchmarks on A100
python model/modal_benchmark.py
```

## How to Add New Results

1. **Create result directory**:
   ```bash
   mkdir -p profiling/results/{gpu}-{platform}-{date}
   mkdir -p profiling/results/{gpu}-{platform}-{date}/plots
   ```

2. **Run benchmarks**:
   ```bash
   python profiling/run_benchmarks.py \
     --output profiling/results/{gpu}-{platform}-{date}/benchmark_results.json
   ```

3. **Generate visualizations**:
   ```bash
   python profiling/visualize.py \
     profiling/results/{gpu}-{platform}-{date}/benchmark_results.json
   ```

   Writes into that same directory, so the four PNGs land in `plots/` and `benchmark_summary.txt` beside them.

4. **Create metadata.json**:
   - Extract metadata from `benchmark_results.json`
   - Add summary statistics and key findings
   - List all files in the result set

5. **Update manifest.json**:
   - Add entry for the new result set
   - Include quick summary of key findings

6. **Commit results**:
   ```bash
   git add profiling/results/{gpu}-{platform}-{date}/
   git add profiling/results/manifest.json
   git commit -m "results: add {gpu} benchmarks from {platform}"
   git push
   ```

## Key Findings Summary

> **Correction, 2026-10-13.** These summaries describe reference implementations, not tuned kernels. The SSM path is a Python for-loop over time steps (one small kernel launch per step) and the attention path is a plain matmul-softmax-matmul, both at batch size 1. Most of the latency gap below is launch overhead. Full reasoning in [analysis/gpu_comparison_t4_vs_a100.md](analysis/gpu_comparison_t4_vs_a100.md).

### Tesla T4 (Google Colab)
- **SSM latency**: 100-202x slower than attention
- **Bandwidth utilization**: 0.05-0.42% of the 320 GB/s peak
- **Compute utilization**: 0.012-0.049% of the 8.1 TFLOP/s peak
- **Arithmetic intensity**: 3.0-6.1 FLOP/byte

### NVIDIA A100 (Modal)
- **SSM latency**: 543-2,382x slower than attention
- **Bandwidth utilization**: 0.012-0.11% of the 1555 GB/s peak
- **Compute utilization**: 0.0004-0.002% of the 312 TFLOP/s BF16 tensor peak
- **Arithmetic intensity**: 3.0-6.1 FLOP/byte

### Cross-GPU Comparison
- Average SSM recurrent latency: 388.312 ms on T4, 319.369 ms on A100. The A100 is 1.22x faster
- Average attention latency: 3.247 ms on T4, 0.233 ms on A100. The A100 is 13.96x faster
- SSM bandwidth utilization: 0.05-0.42% on T4, 0.012-0.11% on A100
- Attention bandwidth utilization: 1.62-3.28% on T4, 1.33-12.3% on A100

Better hardware helps the attention path roughly eleven times more than it helps the SSM path. That asymmetry is real, but it is not evidence about silicon. A workload whose floor is set by Python-loop kernel launches gains almost nothing from extra bandwidth or FLOPs on any GPU, and the near-zero utilization on both sides says neither implementation comes close to saturating the device.

An earlier version of this summary stated that SSM latency was identical on both GPUs at 319 ms. It was not. The T4 metadata summary block had been populated with the A100's averages. The T4's own raw data gives 388.312 ms. Each `metadata.json` now carries a `summary_repair` block naming every field whose stored value contradicted its raw data.

The result that survives every caveat is arithmetic intensity (3.0-6.1 FLOP/byte for SSM, 146-230 for attention), because it follows from the algorithms rather than from our code or from the peak constants.

Whether the GPU-SSM mismatch is architectural is still an open question. It needs fused kernels on both sides (Mamba CUDA kernels, FlashAttention-2), CUDA graph capture for decode, and energy telemetry before it can be answered.

## Data Integrity

All result files are:
- **Immutable**: Once committed, measured values are never modified. If a bug is found, a new result set is created with a corrected run.
- **Reproducible**: Each result set includes full metadata (software versions, hardware specs, configuration) to enable reproduction.
- **Self-contained**: Each result directory contains everything needed to understand and analyze the results.

Immutability covers measurements, not interpretation. The `summary` blocks in each `metadata.json`, and every number in `benchmark_results.json`, are unchanged since 2026-10-10. The interpretive fields (`key_findings` in each `metadata.json`, and `conclusion` in `manifest.json`) were corrected on 2026-10-13, because they asserted a confirmed architectural mismatch that the naive reference implementations in these runs cannot support. Each corrected field says so in its own text and carries the correction date. Analysis documents are corrected the same way, with a dated note at the top.
